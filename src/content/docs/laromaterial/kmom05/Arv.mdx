Arv möjliggör återanvändning av kod genom att låta en klass ärva egenskaper och metoder från en annan klass. Klassen som ärver kallar vi **subklass** och klassen vi ärver ifrån **basklass**. Vi kan se det som att subklassen är en utökning eller en specialisering av basklassen.

Om vi tar klasserna **DeckOfCards** och **Card** är de däremot inte lämpliga att koppla ihop med arv. En kortlek är inte ett speciellt slags kort, utan en kortlek innehåller flera kort. Relationen mellan dessa klasser är därför komposition snarare än arv.  
För att använda arv behöver vi istället klasser där den ena verkligen är en specialisering av den andra. Ett exempel är att låta klasserna **PlayingCard** och **JokerCard** ärva från en mer generell klass **Card**.  
DeckOfCards innehåller Card-objekt vilket är komposition.  
PlayingCard är en Card vilket är arv. Liksom JokerCard är en Card vilket också är arv.

För att visa arv så utökar vi Bankexemplet från artikel [Introduktion till UML och klassdiagram](/laromaterial/kmom02/umlklassdiagram) från kmom02. Vi introducerar ett lönekonto och eftersom "lönekonto är-ett Bankkonto" så är det arv. Dessutom introducerar vi ett räntesparkonto, som också ärver från Bankkonto. De nya kontona har olika aktiviteter varje månad, på räntekontot så får vi ränta varje månad och på lönekontot tas en avgift varje månad.

Skapa gärna ett projekt **MyBank** under "kmom05/practice" och testkör koden.


## Arv med BankAccount

Vi vill specialisera vårt bankkonto till att vara ett räntekonto eller ett lönekonto. Ett räntekonto "är-ett" bankkonto och därför kan räntekonto ärva bankkonto. Då återanvänder vi koden i klassen **BankAccount** och gör två subklasser **InterestAccount** och **PayrollAccount** och utökar dessa subklasser med det som är specifikt för respektive kontotyp. Om vi vill lägga till en tredje kontotyp är det enkelt att göra.

### Implementation

Vi använder klassen **BankAccount** från [kmom03](/laromaterial/kmom03/relationerklassdiagram/#bankexemplet) men ändrar attributet `_owner` till åtkomstnivå protected.

<details>
<summary>
##### Klassen BankAccount
</summary>

```csharp title="Skapa klassen BankAccount i src-katalogen"
namespace MyBank.src;

public class BankAccount
{
    private static int _nextAccountNumber = 100000;
    protected string _owner;
    private decimal _balance;
    private string _accountNumber;

    public BankAccount(string name, decimal initialBalance)
    {
        this._owner = name;
        this._balance = initialBalance;
        this._accountNumber = BankAccount._nextAccountNumber.ToString();
        BankAccount._nextAccountNumber++;
    }

    public string GetOwner()
    {
        return this._owner;
    }

    public decimal GetBalance()
    {
        return this._balance;
    }

    public string GetAccountNumber()
    {
        return this._accountNumber;
    }

    public bool Deposit(decimal amount)
    {
        bool okDeposit = false;

        if (amount > 0)
        {
            this._balance += amount;
            okDeposit = true;
        }
        return okDeposit;
    }

    public bool Withdraw(decimal amount)
    {
        bool okWithdraw = false;

        if (this._balance >= amount)
        {
            this._balance -= amount;
            okWithdraw = true;
        }
        return okWithdraw;
    }

    public void PrintDescription()
    {
        Console.WriteLine($"Kontot med nummer {this._accountNumber} skapades till {this._owner} med saldot {this._balance} kr.");
    }
}

```

</details>

Då skapar vi subklasserna **InterestAccount** och testar den. Med konstruktionen `: BankAccount` visar vi att klassen ärver från `BankAccount` och med konstruktionen  `: base` (direkt efter konstruktorns parameterlista) visar vi att vi anropar basklassens konstruktor.

Subklasserna kommer åt basklassens attribut och metoder som är publika (public) och som är skyddade (protected) men inte de som är privata (private). Nu testar vi att vi kommer åt skyddade attribut men inte privata attribut.

```csharp title="Skapa klassen InterestAccount i src-katalogen"
namespace MyBank.src;

public class InterestAccount : BankAccount
{
    public InterestAccount(string name, decimal initialBalance) : base(name, initialBalance)
    {
    }

    public void PrintDescriptionExtension()
    {
        Console.WriteLine($"Detta räntekonto skapades till {_owner} med saldot {_balance} kr.");
    }
}
```

Vi testar genom att skapa ett objekt av klassen **InterestAccount** och bygger med `dotnet build:

```csharp title="Testkör klassen InterestAccount i Program.cs"
using MyBank.src;

InterestAccount interest = new InterestAccount("Marie savings", 120000);
```

Då får vi följande felmeddelande:  
*error CS0122: 'BankAccount._balance' is inaccessible due to its protection level*  

Det beror på att attributet `_balance` är privat medan attributet `_owner` är protected kan därför nås från subklassen. Men varför ska subklassen komma åt att skriva ut informationen i basklassen? Bättre att låta basklassen skriva ut sin information själv.

```csharp title="Skapa klassen InterestAccount i src-katalogen"
namespace MyBank.src;

public class InterestAccount : BankAccount
{
    public InterestAccount(string name, decimal initialBalance) : base(name, initialBalance)
    {
    }

    public void PrintDescriptionExtension()
    {
        Console.WriteLine($"Räntekonto:");
        base.PrintDescription();
    }
}
```

Och så skapar vi ett objekt av klassen **InterestAccount** och bygger med `dotnet build:

```csharp title="Testkör klassen InterestAccount i Program.cs"
using MyBank.src;

InterestAccount interest = new InterestAccount("Marie savings", 120000);
interest.PrintDescriptionExtension();
// Ger utskriften:
// Räntekonto:
// Kontot med nummer 100000 skapades till Marie savings med saldot 120000 kr.
```

Raden som börjar med "Kontot..." kommer från basklassen och raden som börjar med "Räntekonto:" kommer från subklassen. Åtkomstnivån `protected` används i arv då subklasserna ska komma åt basklassens metoder och attribut.

## Metodöverskuggning med BankAccount

De olika kontotyperna har olika aktiviteter i slutet av månaden men själva aktiviteten är olika för de olika kontona. Då kan vi skapa en metod, `PerformMonthEndTransactions()`, i basklassen som vi sedan överskuggar (override) i subklasserna. För att visa att vi vill att en metod ska överskuggas så markerar vi den **virtual** i basklassen. När metoden är **virtual** i basklassen så är det ett erbjudande om att subklassen kan överskugga metoden. Om metoden ska överskuggas i subklassen så används **override** subklassens metod.

### Implementation

Vi skapar en virtuell metod `PerformMonthEndTransactions()` i klassen **BankAccount** som returnerar false som standard. Eftersom vi har en returtyp på `PerformMonthEndTransactions()` så måste vi ha en return-sats i den.

```csharp title="Lägg till en virtual metod PerformMonthEndTransactions i klassen BankAccount"
namespace MyBank.src;

public class BankAccount
{
    private static int _nextAccountNumber = 100000;
    protected string _owner;
    protected decimal _balance;
    private string _accountNumber;

    public BankAccount(string name, decimal initialBalance)
    {
        _owner = name;
        _balance = initialBalance;
        _accountNumber = _nextAccountNumber.ToString();
        _nextAccountNumber++;
    }
    ...

    public virtual bool PerformMonthEndTransactions() { return false; }
}
```

Nu ska vi implementera metoden i subklasserna. I klassen **InterestAccount** så får alla en liten ränta och de som har mer pengar får mer ränta. Räntan sätts även in på kontot.

```csharp title="Klassen InterestAccount gör override på metoden PerformMonthEndTransactions"
namespace MyBank.src;

public class InterestAccount : BankAccount
{
    public InterestAccount(string name, decimal initialBalance) : base(name, initialBalance)
    {
    }

    public override bool PerformMonthEndTransactions()
    {
        decimal interest = 0.01m;
        decimal balance = base.GetBalance();

        if ( balance > 100000m)
        {
            interest = 0.02m;
        }

        return Deposit(interest * balance);
    }
}
```

På lönekontot erbjuder Banken olika tjänster och därför tar de ut en liten avgift varje månad. De som har mycket pengar på lönekontot betalar en större avgift. Notera att vi lägger till ett m efter flyttalet för att få typen "decimal" som används vid beräkningar med stor precision.

```csharp title="Klassen PayrollAccount gör override på metoden PerformMonthEndTransactions"
namespace MyBank.src;

public class PayrollAccount : BankAccount
{

    public PayrollAccount(string name, decimal initialBalance) : base(name, initialBalance)
    {
    }

    public override bool PerformMonthEndTransactions()
    {
        decimal fee = 1.0m;

        if (base.GetBalance() > 100000m)
        {
            fee = 200.0m;
        }

        return Withdraw(fee);
    }
}
```

För att testa implementationen har vi denna kod i huvudprogrammet:

```csharp title="Vi testar metoden PerformMonthEndTransactions i huvudprogrammet"
using MyBank.src;

var account = new BankAccount("Marie", 1000);

account.PrintAccountDescription();

// Kontot med nummer 100000 skapades till Marie med saldot 1000 kr.

```


## En tumregel från ”god OOP-design”

*Exponera inte data — exponera beteende.*
Fundera alltid på vad en subklass behöver kunna göra, inte vilka attribut den behöver komma åt.

### Varför är protected attribut ofta dålig design?

Att exponera attribut direkt, även som protected, kan skapa flera problem:

1. Subklasser blir beroende av implementationen  
Subklasserna måste känna till hur basklassen lagrar sin data. Om basklassen senare ändras kan befintliga subklasser behöva skrivas om.

1. Svårare att skydda objektets tillstånd  
Basklassen kan ha regler som alltid ska gälla. Om subklasser får ändra attribut direkt blir det svårare att säkerställa att objektet alltid befinner sig i ett giltigt tillstånd.

1. Ökad koppling mellan klasserna  
Arv innebär redan en stark koppling mellan basklass och subklass. Direkt åtkomst till basklassens data gör kopplingen ännu starkare och minskar flexibiliteten.

### Rekommenderad praxis

Använd i första hand:

- `private` attribut
- `protected` metoder när subklasser behöver utöka eller anpassa beteendet

På så sätt behåller basklassen kontrollen över sitt tillstånd samtidigt som subklasserna kan återanvända och bygga vidare på funktionaliteten.
